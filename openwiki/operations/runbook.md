# Installation, update, and recovery runbook

Use the installer preflight and dry-run/plan path before changing an adopter. Review the artifact catalog and release ledger, then apply a plan through `packages/codekeeper/src/cli.mjs`; failed writes use installer rollback. Updates preserve explicitly opted-in profile overrides while advancing packaged defaults and handling renamed or retired assets.

Installer progress stages are startup-variable mutation, secret upload, generated-file commit, push, and pull-request creation. `reportProgress` identifies the active stage; `runMutation` records timeout, truncation, or command failure as a resumable error. Before retrying, check clean status, branch and remote SHA, generated-file digests, startup enablement, open PR state, and any managed marker/lease. The installer exposes the exact recovery command in its formatted error; treat that emitted command and error code as the contract because flags can vary by release. At each stage, the operator action is deterministic: after startup-variable failure, rerun the emitted init command only after querying variables; after secret-upload failure, rerun the emitted init command after checking which secrets were accepted; after commit failure, run the emitted resume command on the expected branch after `git status`; after push failure, run the emitted resume command only when local and remote SHAs match the error’s expected values; after PR failure, run the emitted resume command after checking for an existing setup PR. Never invent a force operation. Pre-commit failures may use the printed resume/retry command after rollback; settings failures resume after confirming startup variables/secrets; commit failures resume after cleaning or preserving the expected generated branch; push failures resume only after remote SHA comparison; PR failures resume by opening or recognizing the existing setup PR. Settings, push, and PR failures require the printed manual-resume or rerun path only after reconciling the changed external state. A startup-variable failure can leave enablement unchanged or partially applied; secret-upload failure can leave earlier secrets present; commit failure can leave the local branch dirty; push failure can leave a remote branch; PR failure can leave a pushed branch without a PR. A failure before commit may be rolled back automatically; after settings, push, or PR mutation, assume external state changed and reconcile manually before resuming.

For runtime incidents, inspect the run-scoped artifact and hash mismatch first, never print credentials, and rerun only after determining whether preparation, validation, or publication failed. A failed validation is safe to rerun. A publication failure requires checking managed markers, App identity, current PR/issue state, and any repair lease before retrying. Stale expected heads, protected branches, or foreign markers must be repaired by reconciling live GitHub state, not by forcing a write.

Rotate provider, Codex, trace, and App credentials independently. Remove a capability in policy before removing its secret. Do not reuse trace credentials as provider credentials. The repository's acceptance recovery scenarios and installer rollback/trust tests are the narrow validation evidence for these procedures; broad `npm run check` is required for lifecycle implementation changes.
